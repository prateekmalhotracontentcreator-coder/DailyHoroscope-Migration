## Architecture Notes (Permanent)

- **C-score formula:** `C = 0.40×polarity_delta + 0.35×timing_delta + 0.15×strength_delta + 0.10×authority_delta`
- **Contradiction flag:** C ≥ 0.55
- **Representation modes:** `synthesis` (C < 0.30) · `tension` (0.30-0.75) · `honest_uncertainty` (C > 0.75)
- **β/γ multipliers:** range 0.78-1.22 · computed from questionnaire · stored in `user_questionnaire_profiles`
- **Approval levels:** `auto_approved` = AI validation passed (NOT live to users) · `approved` = co-founder signed off (ONLY this reaches users)
- **DB:** all ingest targets `horoscope_db` -- do NOT use stale `EverydayHoroscope` DB
- **Cross-system rule co-occurrence (LK + BPHS):** When two textbooks share a planet×house input key but produce different outputs (e.g. LK wave rule vs BPHS natal prediction), this is NOT a data conflict requiring a patch. The fix is at the **engine interpretation layer**: `scan_chart()` / the query router selects which rule categories to invoke based on the **nature of the user's query** (psychological/personality query → LK wave rules; life event query → BPHS rules; remedy query → LK prohibition/remedy rules). Rules from different systems never compete in the same response because the query router prevents co-invocation. No source-system tagging needed on the rules themselves for contradiction suppression.

## Layer B Architectural Rulings (Locked 2026-06-09)

These rulings govern how Layer B accuracy is tested and how rules must be encoded. They are co-founder decisions -- do not override without explicit approval.

**Rule corpus for Layer B testing:**
> Include `approved` + `auto_approved` + `pending_human_review` (≈10,234 rules). Exclude: `flagged`, `rejected`, `deprecated`. PHR rules are structurally valid, textbook-decoded rules that passed AI validation -- their PHR status reflects only pending TT review, not suspected incorrectness. Testing 60% of the corpus (approved+auto_approved only) is insufficient.

**KP condition types -- Engine gap, zero tolerance:**
> `_condition_matches` in `knowledge_engine.py` must implement handlers for `kp_planet_signification`, `kp_star_lord`, `kp_csl`, and `kp_signification_chain`. The T05 sub-lord table (`KP_T05_Master_Sub_Significance.json`, 249 entries) must be loaded at engine startup and used as the lookup source. Without these handlers, every KP textbook rule returns `False` unconditionally -- the entire KP corpus contributes zero signal. This is a **backend engine change** (KE-OP-18). The unique flavour of KP astrology in the KE is the justification for having decoded the KP textbooks; it must be evaluable.

**Multi-factor observations → single composite rule, exact match:**
> If an author observation requires N simultaneous conditions, it MUST be encoded as ONE rule with `type: "composite"`, `operator: "AND"`, and N sub-conditions. No tolerance. Either all N conditions pass → rule fires; else → rule does not fire. This is an ingest encoding standard. Existing rules that violate this (N separate single-condition rules for what should be a composite) must be identified and re-encoded. Layer B gap report surfaces these as precision failures.

**Niche chart configurations -- corpus gap, not test tolerance:**
> Every chart configuration that appears in a test vector textbook must have a corresponding rule in the KE corpus. A Layer B zero-Jaccard vector is not "niche" -- it is a **corpus gap** (missing rule). The Layer B ⚠️ output lines (fired=[] expected=['career']) form the corpus gap registry. Each zero-Jaccard vector is a rule ingest task, not a tolerance item. Exact match required.

**Dasha-gated observations -- `dasha_active` is mandatory:**
> If a textbook observation is conditional on a specific dasha period ("during Saturn dasha X manifested"), the encoded rule MUST include `dasha_active: "Saturn"` in its condition dict. A rule without this gate will over-fire -- it fires for ALL people with that natal configuration regardless of dasha, producing wrong answers for people in the wrong dasha period. `_condition_matches` already handles `dasha_active` (line 671). The gap is in rule encoding. An audit pass is required on existing dasha-conditional rules. Layer B precision failures (rule fires but shouldn't) will surface candidates.

**Primary and Secondary Axis -- explicit declaration, no guesswork:**
> Every rule must declare `claim_axis` (primary, already exists in schema). Rules that fire on a secondary life area must declare `secondary_axis` (new field -- needs schema addition to `ke_schema_constants.py` and `knowledge_schema.py`). Layer B scoring uses both fields: `fired_axes` is built from `claim_axis` + `secondary_axis` of all rules that fire. Axis inference from `categories` list ordering is a stopgap only -- the final standard is explicit `secondary_axis` field. The `AXIS_NORM` mapping in `phase4_layer_b.py` (granular → coarse vocabulary) remains until all rules are updated with explicit axis declarations.

**Layer B gate: exact match at claim-axis level:**
> Layer B pass = fired_axes ∩ expected_axes = expected_axes (recall = 1.0 for that axis set). Jaccard ≥0.85 per vector is the minimum acceptable score. Target is not 85% of vectors passing -- it is all tested vectors passing (100%), with the 15% tolerance representing only vectors with KP condition type gaps (KE-OP-18) or dasha-gate encoding gaps (both of which are engine/encoding issues to be fixed, not permanent tolerances). Once KE-OP-18 (KP conditions) is implemented and dasha-gate audit is done, the tolerance drops to ≤5% (data quality only).

**LLM-as-Judge (Layer C) is mandatory before KE-OP-4:**
> Layer B confirms that the right TOPICS are covered. Layer C confirms that the interpretation TEXT is accurate. A rule can correctly fire on `career` axis but have wrong or generic interpretation text -- Layer B cannot catch this. Layer C (LLM-as-Judge scoring ≥4.5/5 on reasoning rubric) is the gate for interpretation quality. Neither layer replaces the other. Both must pass before KE-OP-4 (co-founder sign-off).
